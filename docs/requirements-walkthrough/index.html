00 客户端总体设计

我们要构建一个面向运维场景的桌面客户端。 用户在客户端管理 Agent 与 Skill、进行本地编辑和实验，并由 Agent 通过 Playwright 操作随客户端交付的内置 Chrome 完成运维任务。这里的“内置 Chrome”实际采用 CEF／Chromium 内核，页面直接展示在客户端工作台中。

我们的核心资产是受版本控制、可持续演进的 Agent 提示词与 Skill。 提示词沉淀任务目标、操作边界和结果要求，Skill 完整文件包沉淀可复用的运维方法、操作步骤和参考资料。团队按周将实际任务中的反馈转化为改进，经本地编辑、按需实验后发布新的确定版本，逐步提高 Agent 的任务完成能力。

客户端支持用户主动发起会话，也能连接已有内部服务，接收远端 Agent 调用并回传结果。本设计围绕客户端的界面、资源管理、运行与恢复展开；各章最后列出服务端需要配合提供的能力。

US

界面设计

客户端由左侧导航、中央内容区和右侧工作台组成。导航组织会话、Agent 与 Skill；中央区域承载编辑和对话；工作台展示浏览器与执行过程。账号区域展示用户身份与运维权限，连接状态区分已连接、重连中和离线。

  1. 作为运维人员，我希望在客户端编辑、实验并发布 Skill 和 Agent，让团队使用确定的版本。
  2. 作为普通用户，我希望同步并使用官方能力，也能自由编辑自己的本地资源。
  3. 作为用户，我希望客户端能接收服务端任务，由 Playwright 在内置 Chrome 完成操作，并在同一个工作台查看真实页面、执行过程与结果。
  4. 作为用户，我希望知道运行了什么、结果是什么，并在断线后仍能交付已有结果。
  5. 作为用户，我希望客户端出问题后能上传指定 thread 的诊断材料，并取得服务端确认接收的编号。

简要设计

客户端把资源管理和任务执行放在同一个工作空间中：用户编辑、实验和选择 Agent，客户端准备所需物料，在专用 Chrome 中执行，并保存可查看、可补传的结果。Tauri 承担桌面包装，本次不引入其他 Rust 业务模块作为前置条件。

客户端保留未同步编辑、已下载历史版本、会话快照与执行记录。本地资源可自由编辑；官方已发布资源同步后只读，服务端只调用官方 Agent。

Playwright 与内置 Chrome

执行链路：用户或服务端任务 → 客户端 LangGraph Agent → 所选 builtinTool → Playwright → 本地 CDP → 内置 Chrome 页面。 模型负责决定步骤，Playwright 负责页面检查和操作，内置浏览器承载真实网站与登录态；右侧工作台展示的就是被操作的页面。

组成 职责
Tauri 业务界面 管理 Agent、Skill、会话与执行记录；与网站浏览器视图分开
本地 Node.js／LangGraph runtime 装配固定快照、调用模型与所选工具，控制单任务执行、停止和超时
Playwright 通过宿主提供的本地 CDP 地址和精确页面 ID 连接浏览器，执行页面检查与脚本；页面匹配失败时结束本次操作
内置 Chrome（CEF／Chromium） 原生宿主管理并嵌入工作台的真实浏览器，使用应用专用 profile 保存 Cookie 与登录态

Node.js、Playwright 和 CEF 随桌面整包交付，用户无需另行安装 Chrome 或自动化运行环境。业务界面仍使用 Tauri 的系统 WebView；网站页面使用内置 CEF 浏览器，不把业务 UI 当作运维目标页面。浏览器版本与工具实现由桌面版本确定，更新规则见第 05 章。

页面检查、脚本保存与执行都在本机完成。脚本执行时保存源码快照并核对调用方指定的内容摘要，结果、截图等产物关联执行记录；脚本沿用宿主指定的页面。任务从准备到停止排空期间独占浏览器，用户可以查看过程，手动导航和页面输入等待任务结束。遇到人工登录或验证，本轮结束；用户在同一浏览器完成操作后显式发起新一轮。停止不回滚已发生的外部操作，也不自动续跑。

打包客户端已具备内置浏览器截图保存能力。 run_playwright_script 在脚本结束时尝试截取同一个 CEF 页面的当前视口，将 screenshot.png 保存到该会话的脚本执行产物目录；普通脚本报错也会尝试保存。取消／超时导致进程强制结束或浏览器崩溃时，截图可能缺失。当前会话展示工具结果，截图文件留在本地产物中，尚未直接作为聊天图片显示。

专用 profile 与用户日常浏览器隔离，网站 Cookie、登录态及本地 CDP 地址不作为服务端任务材料上传。故障时按第 09 章导出指定 thread 的脱敏证据，不上传整个浏览器 profile。

当前本地链路的代码依据：浏览器连接、页面匹配、脚本执行、macOS 原生视图与 Windows 原生视图。服务端远端调用仍为待接入能力，接口汇总见服务端 API。

场景二：客户端接收远端调用

服务端配合

为支持上述客户端能力，已有内部服务需要提供：

  • 身份与权限：复用已有账号与 Token，返回用户身份与运维权限，并校验官方资源写入；普通用户不能写入官方资源。
  • 草稿、发布与同步：保存官方草稿修订和不可变发布版本，提供 HTTPS 清单与文件包；Skill 正式发布时联动受影响 Agent，所有标签由运维人员手填，不增加审核。
  • 资产持续演进：保留每周发布涉及的提示词、Skill 和 Agent 装配关系，让客户端能够查看新旧版本及本次改进；不为周发布新增定时自动发版、MCP 发布或独立提示词版本系统。
  • 调用与结果确认：LangGraph 将客户端 Agent 作为工具调用，通过 WebSocket 传入上下文、按调用 ID 取消，接收状态、结果、快照并确认；客户端返回忙时由服务端安排后续调用。
  • 桌面更新来源：提供更新清单和已签名整包下载，供客户端检查、下载与校验。
  • 诊断接收：接收用户指定 thread 的诊断包，校验并持久保存后返回回执，支持运维按编号只读查看；不会因此恢复或重新执行任务。

服务端高可用和内部编排实现另行定义；客户端依赖的 HTTPS API、WebSocket 消息和接收确认契约统一见 10 · 服务端 API。

01 · SKILL

串讲重点：客户端提供 Skill 列表与包内文件管理，支持文件级上传、编辑和实验；运维人员上传完整草稿、发布完整文件包，服务端配合保存和分发。

US

界面设计

Skill 页面分为两层：列表管理 Skill，进入一个 Skill 后管理包内目录与文件。资源标明本地或官方来源，版本记录以完整文件包为单位。用户上传、查看和编辑具体文件，在页面选择 Agent 发起草稿实验；运维人员可上传草稿，并手填 Skill 与受影响 Agent 的标签完成联动发布。

  1. 作为运维人员，我在客户端编辑草稿并按需上传，让服务端集中保存修订。
  2. 作为运维人员，我在 Skill 页面勾选一个 Agent，即可实验尚未上传的草稿。
  3. 作为运维人员，我手填 Skill 和受影响 Agent 的新标签，一次完成正式发布。
  4. 作为用户，我使用官方已发布 Skill；需要修改时复制成本地 Skill，保留官方原件。
  5. 作为用户，我能在列表中找到、新建或复制 Skill，进入后向指定目录上传文件，并看到每个文件的保存结果。

简要设计

客户端围绕“编辑 → 实验 → 上传或发布”组织 Skill 操作。用户可以自由编辑、保存本地 Skill，不设发布标签；在页面勾选现有 Agent，就能运行尚未上传的草稿。实验前固定完整快照，日志、截图等实验产物另存。

客户端按整个文件包保存和装配 Skill，包括说明、脚本、引用资料和随包资源。官方发布包只读，普通用户可同步、查看和使用；运维人员可上传草稿修订、发布新版本。服务端配合集中保存这些官方物料，客户端保留未同步编辑、下载缓存和已下载的历史版本。

页面区域 内容与操作
Skill 列表 标题「Skill」；按名称搜索；全部、本地、官方筛选；默认列表，每行显示名称、简述、来源，以及本地已保存 / 未同步编辑 / 草稿修订 / 正式标签等对应状态。点击进入该 Skill。

包内文件管理 面包屑显示「Skill / 名称 / 当前目录」；目录导航和文件列表显示名称、类型、大小及操作结果。选中文件后阅读或编辑，保留源码、预览、分栏三种阅读方式。
可编辑内容 「上传文件」支持选择或拖入多个文件，加入当前目录；「新建文件」「新建文件夹」及重命名、删除作用于当前本地内容或官方草稿。上传说明、脚本、图片及附件均保留实际文件内容和相对路径；不支持预览的文件仍可保存。
官方发布版本 展示人工标签和版本轨迹；目录与文件只读，可查看、复制为本地或由运维人员转入草稿维护。切换版本不覆盖本地已下载历史包。

02 · MCP

串讲重点：客户端随 Agent 获取 MCP 配置，连接远端 MCP 并展示调用过程；服务端配合提供官方配置。

US

界面设计

MCP 位于 Agent 的能力配置区，支持选择服务、查看工具/资源/提示词清单，以及展示连接配置或引用、连接状态和失败原因。官方 Agent 的配置只读；配置随 Agent 同步，MCP 服务本身不纳入发布版本。

  1. 作为运维人员，我为官方 Agent 配好所需 MCP，让用户同步 Agent 后获得对应配置。
  2. 作为用户，我通过客户端连接远端 MCP，包括内部服务提供的 MCP，执行 Agent 所需操作。
  3. 作为用户，我查看当次启用的 MCP 和工具清单，了解运行时实际使用了哪些能力。

简要设计

用户在客户端的 Agent 能力区选择 MCP、查看能力清单；客户端运行 Agent 时，按装配配置连接对应的远端 MCP 并调用工具。MCP 可以来自内部服务，也可以来自其他已配置的远端地址。

官方 Agent 所需的 MCP 连接配置或引用随 Agent 一并同步，客户端保持只读；本地 Agent 使用自己的配置。配置选择参与 Agent 内容 ID，更改官方装配需要形成新的 Agent 版本。外部 MCP 服务实现本身不进入本项目的版本与发布体系，不固定其工具行为或发布周期。

客户端

  • 随官方 Agent 同步所需 MCP 连接配置，按当次装配建立远端连接并使用工具。
  • 官方 Agent 的 MCP 配置保持只读；本地 Agent 按自身配置使用 MCP。
  • 在会话中展示工具调用过程；运行快照记录启用的 MCP 与工具清单。
  • 密钥和 Token 不进入运行快照；配置的同步不意味着将凭据写入可观测记录。

详细设计

运行模型一：连接成功并调用 MCP

条件： 客户端已固定本轮使用的 Agent 装配；官方 MCP 配置或引用随 Agent 同步，本地 Agent 使用自己的配置。所需远端 MCP 可用。

打开交互顺序图：MCP 连接与调用

结果： 客户端取得能力清单后执行所需工具调用，展示过程，并将工具结果纳入本轮任务结果。运行快照记录启用的 MCP 与工具清单，不包含密钥和 Token。图中的 Agent 物料是当次装配，不表示每次工具调用都重新同步。

运行模型二：所需 MCP 连接失败

条件： 本轮所需 MCP 无法连接或鉴权失败。调用方可以是用户或发起远端任务的服务端。

打开交互顺序图：MCP 连接失败

结果： 客户端不进入该 MCP 的工具调用，记录并展示失败原因；远端任务按任务结果回传规则通知服务端。连接成功后若实际工具调用失败，同样记录该调用错误并纳入本轮失败结果，不把失败伪装为成功。

MCP 可以由内部服务或其他远端服务提供。服务端作为配置来源、MCP 作为工具服务，是两个职责，部署在同一处也不合并其含义。MVP 不增加 MCP 发布标签、服务实现下载、独立升级器或监控平台；具体鉴权方式和传输参数随实际接入确定。

服务端配合

为支持客户端获取配置、连接 MCP，服务端需要配合：

  • 将官方 Agent 所需 MCP 配置或引用纳入 Agent 物料，提供同步。
  • 校验官方配置写入者的运维权限，向普通用户提供已发布配置。
  • 若由内部服务提供 MCP，提供可供客户端连接的接入点；其内部实现和发布流程不在本规格范围内。

LangGraph 编排流程时调用客户端 Agent；客户端承担实际执行及 MCP 调用。MCP 的来源不改变这一边界。

  • 工具齐全后按 Agent 装配执行，并在客户端展示工具调用过程。
  • 运行快照记录启用的工具清单和桌面端版本；调用状态、错误与起止时间仍放入执行记录。

详细设计

运行模型一：所需工具齐全

打开交互顺序图：builtinTool 齐全

运行模型二：缺少所需工具

条件： 运行前发现至少一个 Agent 所需 builtinTool 不在当前桌面版本中。

打开交互顺序图：builtinTool 缺失

结果： 本轮直接失败，不开始 Chrome 操作。客户端列出缺失工具并提示更新桌面端；远端任务回传失败原因。完成更新后由用户或服务端重新发起调用，不自动重跑该失败任务。

  • 在官方 Agent 物料中提供所需 builtinTool 清单。
  • 接收运维人员提交的工具选择变更，按 Agent 发布规则生成新的 Agent ID、保存手填发布标签。
  • 远端调用失败时，接收客户端返回的工具缺失结果，决定后续处理。

builtinTool 实现由桌面应用交付，服务端物料同步不单独分发工具实现，也不将其混入 Skill 文件包。

运行条件 当前会话实际选用的模型、推理参数与桌面版本 模型实例和运行环境 记录在运行快照，不因模型参数变化发布新的 Agent

配置保存的是“本次需要哪些能力”，运行装配则将它们解析为实际文件和可调用工具。MVP 保持 MCP 服务级选择：连接选中的服务并取得工具清单，不新增逐工具授权管理界面。密钥、Token 从运行时凭据来源取得，其值不进入发布指纹或快照。

与每周资产发布的关系

Agent 提示词和 Skill 是持续改进的核心资产。只修改提示词时，发布新的 Agent，原 Skill 包继续复用；修改 Skill 时，正式发布完整新包，并一次更新所有受影响官方 Agent 的引用、内容 ID 和人工新标签。周内编辑与保存草稿不联动，按周选择已确认的改进发布；详见总体设计中的周迭代。

**结果：**相同版本不重复下载。客户端检查 builtinTool 并固定运行快照后，才进入执行流程；本地有旧包不代表可以跳过所需版本的核对。

**条件：**核对清单失败，或者下载所需物料失败、物料不可取得。任一条件都直接结束本次准备，不再继续后面的装配与执行。

  • 使用与客户端相同的 Skill 版本相对目录、包内路径、内容 ID 算法及标签映射；只有完整包与关联 Agent 均可取得后才公布正式发布结果。
  • 远端调用明确所需 Agent 版本，客户端据此核对；具体字段和端点留到实现阶段确定。
  • 保留已发布版本和标签的不可变关系。Skill 发布产生新 Agent 装配，不改写历史版本。
  • 按现有身份体系开放相应读取和运维写入能力，不新增客户端账号体系。

串讲重点：客户端出问题后，用户选择一个 thread，将 SQLite 中已落盘的 checkpoint、执行记录和运行快照导出为诊断包；服务端校验、保存并返回接收回执，运维据此排查。

本章是新增设计，上传接口、SQLite checkpointer 和诊断页面尚未实现。 文档阅读页的「本章评论」用于串讲时记录意见，不属于客户端产品的会话功能。

US

  1. 作为用户，我能选择出问题的 thread，说明现象，预览将要上传的内容后提交，不必上传整台客户端的数据。
  2. 作为用户，客户端重启后仍能取得已落盘的 checkpoint；主界面打不开时也有独立的诊断导出入口。
  3. 作为用户，我能区分「正在上传」「接收待确认」「服务端已接收」和「上传失败」，断网后重试不会重复生成工单材料。
  4. 作为运维人员，我能在服务端按诊断编号找到来源 thread、各轮运行、checkpoint 和故障位置，看到材料缺失与脱敏说明。
  5. 作为运维人员，查看故障材料不会启动模型、MCP、浏览器或恢复原任务；浏览器操作结果不确定时保留“结果未知”。

简要设计

checkpoint 固定存放在客户端本地 SQLite。 SQLite 仅承担客户端图状态的持久化，不改变业务服务端使用 PostgreSQL 的约定。诊断上传走 HTTPS，与 WebSocket 上的任务调用、取消和最终结果回传分开。

对象 用途与边界
业务 thread 用户看到的一次会话，包含多个 run；上传范围以这个 thread 为边界
run 用户明确发起的一轮执行；失败、取消或重启中断后不自动重跑
SQLite checkpoint 保存该轮 LangGraph 图状态、父子关系和待提交写入等证据；不能用聊天消息代替
运行快照 固定 Agent、Skill 内容身份、工具、MCP 清单、模型参数与客户端版本
诊断包 某个导出截止点的不可变材料，包含一个 thread 及其关联 run、checkpoint、记录；脱敏后用于排查
接收回执 服务端完成校验与持久保存的证明，包含诊断编号与包摘要；不同于任务结果确认

当前实现与新增部分

当前 runtime.mjs 每轮新建 MemorySaver，checkpoint 随进程退出丢失。run-store.ts 已将 .records 的事件、结果与状态，以及 .sessions 的消息、快照和 lastRunId 保存到磁盘；这些文件是执行记录与会话历史，不是完整的 LangGraph checkpoint。

新增 SQLite 持久化后才能承诺“崩溃后上传已提交 checkpoint”。旧版历史只导出已有记录，并明确标记 checkpoint-missing，不从消息推造 checkpoint。LangGraph 官方持久化说明也区分了内存 saver 与可跨重启保存的持久化 saver。

客户端

从执行记录上传

在执行记录详情增加「上传诊断」入口，也可在运维页按 thread ID 搜索。页面展示会话标题、thread ID、关联 run、状态、最后更新时间、checkpoint 可用情况、材料大小，以及问题描述输入框。上传前明确显示接收服务和当前账号。

用户查看材料清单与脱敏摘要后提交。完整 thread 的已保存消息、工具过程、运行快照与 checkpoint 是主要材料；截图、脚本和其他产物作为明确列出的可选附件。用户取消准备或上传，不取消原任务，也不删除原会话。

客户端已有 Playwright 脚本结束时保存内置 CEF 页面视口截图的能力，上传复用该 run 关联的已有产物。强制终止、超时或浏览器崩溃可能没有截图，此时明确列为缺失；不自动打开网站补拍，也不将稍后拍摄的页面冒充故障时现场。截图的消息展示与诊断上传仍按各自完成情况实现。

首版只导出已结束或已排空写入的 thread。目标 thread 正在准备、执行或停止时，提示等待，或由用户主动停止后再导出；不为了上传偷偷停止任务。其他 thread 可以继续使用客户端。

上传状态为：准备材料 → 待用户确认 → 上传中 → 接收待确认 → 已接收／失败。服务端回执带材料不完整标记时，显示「已接收，材料不完整」及具体原因，不显示“完整恢复成功”。

主界面无法打开

提供不依赖主 UI、浏览器和 Agent 启动的诊断导出入口，可列出本机 thread 并按 ID 导出。它只读取当前用户有权限的本地数据，不启动任务、不调用模型、不初始化 MCP，也不要求执行记录全部正常才能打开。

某条记录损坏时，保留原件，继续收集该 thread 的可读材料，将损坏项记入清单。无法可靠确定记录属于所选 thread 时，不将它混入包。SQLite 完全不可读时，仍可导出会话／执行记录及 SQLite 错误类别，标记 checkpoint 缺失；不自动修库或上传整个数据库。

网络或登录不可用时，先导出本地诊断包。客户端恢复后可选择同一个包上传；运维也可在有权限的服务端接收页上传该包，服务端使用相同的接收校验。导出成功不等于服务端收到。

详细设计

1. SQLite 持久化与执行隔离

  • SQLite 放在用户私有的应用数据目录，例如 <localRoot>/checkpoints.sqlite，不随安装包分发，不写入 Git，也不放进 Skill 包。数据库及其 WAL／SHM 文件遵循同一用户访问边界。
  • 优先使用官方 @langchain/langgraph-checkpoint-sqlite 的 SqliteSaver，通过 getTuple／list／put／putWrites 保存和读取 checkpoint 与 pending writes；启动时校验 schema／序列化版本，事务提交成功才记为“已持久化”。SQLite 存储失败须明确反馈，不能静默回退为内存并继续声称可恢复。
  • 启用 WAL，使用 synchronous=FULL，并为读取与写入设置有界等待；不将 NORMAL 描述为断电后仍保留所有已确认提交。SQLite 将 WAL 合并回主文件的 checkpoint 与 LangGraph checkpoint 是两个不同概念。失败处理保留业务侧已发生操作的“不确定”状态，不因存储错误自动重试模型或工具。数据库升级前保留可恢复副本，失败时不清空旧库。
  • 按 run 隔离图执行状态，按业务 thread 聚合归档。 本地保存 threadId → runId → graphThreadId 的映射，每个 run 有独立的图执行标识；根图、子图继续保留各自的 checkpoint_ns。包内记录映射，不假定业务 thread ID 与图 thread_id 永远相同。
  • 现有实现每轮将保存的消息重新交给新图。接入 SQLite 时保留这一执行语义，避免直接复用旧图状态再输入全量历史，造成消息重复或挂起任务继续执行。用户继续会话会创建新 run，不对失败 run 调用 resume。
  • 正常退出前排空已发起的 checkpoint 写入；强退后只承诺已提交部分。checkpoint 未记录到某个工具结果，不代表外部操作没有发生。
  • 保留策略按 thread／run 管理，不能删除仍被保留 checkpoint 依赖的祖先或增量数据。正在导出的材料在冻结完成前不被清理；超出容量时明确告知，不能无限增长或静默裁剪。

SQLite checkpointer 的具体依赖版本须与已锁定的 LangGraph、checkpoint 接口及 Node 26.11.1 兼容。官方 SqliteSaver 依赖 better-sqlite3 原生模块，而现有打包准备脚本使用 npm ci --ignore-scripts；实现时必须补上目标平台的原生产物准备与校验，仅添加依赖不足以交付。macOS ARM64 与 Windows x64 分别准备匹配目标架构和 Node ABI 的产物，并在对应平台实际加载验收；不能直接复制 macOS 的 native addon 到 Windows 包。WAL 与同步策略的语义以 SQLite 官方说明为准。

2. 固定一个可核查的导出截止点

  1. 解析用户所选的业务 thread ID，取得其 run 与图标识映射；校验归属，不接受用户输入任意磁盘路径。
  2. 取得该 thread 的短期导出锁，阻止它开始新一轮；等待已发起的工具、记录与 checkpoint 写入结束。等待超时则失败并保留当前任务状态。
  3. 在 SQLite 一致性读事务中读取该 thread 对应的各 run、全部 namespace、checkpoint、父关系及 pending writes，同时冻结会话和执行记录副本。现有多个 JSON 文件分别原子写入并不构成跨文件事务，必须由同一 thread 锁协调。
  4. 在清单记录每个 run／namespace 的截止 checkpoint ID、最后事件序号、采集时间与已知状态。冻结后释放导出锁，后续新消息不进入这次包；需要包含它们时生成新的上传 ID。
  5. 对冻结副本进行脱敏、材料校验和压缩，计算包摘要。只读原始 SQLite；不直接复制正在使用的 .sqlite 文件而遗漏 WAL，也不把整库、WAL、SHM 上传给服务端。按映射使用绑定参数查询并生成全新的逻辑包，不能用“复制全库再删除其他 thread”的方式导出，因为删除页仍可能残留其他会话数据。

崩溃后的首次诊断读取应先保留磁盘上的故障证据，再由正常启动流程标记未完成 run 为“执行中断、结果未知”；导出清单分别说明磁盘观测状态和恢复判定。缺失、截断、损坏或尚未提交的尾部数据均有明确记录。

3. 单个 thread 的诊断包

材料 必须说明的内容
manifest.json 格式版本、上传 ID、来源客户端安装标识、业务 thread ID、run 映射、客户端／引擎／checkpointer 版本、截止点、文件字节数与 SHA-256、脱敏策略版本、缺失清单
thread.json 会话标题、已保存消息、问题描述、来源标识；不附带其他 thread

运行快照 实际 Agent／Skill 内容身份、模型参数与工具清单；仅引用包内的相对路径
checkpoint 归档 每个图的 thread_id、checkpoint_ns、checkpoint_id、checkpoint 本体、metadata、父 checkpoint 关系、pending writes 及其任务／通道关联与顺序
可选附件 用户勾选的截图、脚本及相关产物；按清单校验摘要，缺失文件明确列出

checkpoint 导出须包含解释图状态所需的祖先、版本与增量依赖，不只保存最新 messages 或一次 getState() 的输出。通过受控序列化转成可检查的 JSON 数据，保留类型与序列化版本；无法安全解释的值标记缺失，不让服务端执行反序列化代码。

所有材料统一处理凭据与敏感字段，包括 checkpoint、metadata、pending writes、工具参数／返回值和附件。默认排除 API key、Token、Cookie、认证头、环境变量文件、浏览器 profile、系统钥匙串和无关本地文件。现有密钥字符串替换不等于完整脱敏；截图和自由文本也需要预览与选择。脱敏不回写本地原件。

诊断包用于定位问题，脱敏或缺失后的包不承诺能还原为可执行的 saver。Agent／Skill 的完整源包按需另行提供，不能因为上传一个 thread 就扫描并上传所有物料。

4. 上传与服务端接收

首版使用单包 HTTPS 上传＋接收状态查询，不增加分片协议。客户端持久保存不可变包、摘要和上传 ID；同一个包重试复用 ID，材料变化则使用新 ID。下面是待实现的最小接口契约；鉴权、错误与其他服务端接口统一见 10 · 服务端 API，具体路由可在接入已有平台时适配命名：

接口 请求 成功含义
PUT /api/diagnostics/thread-uploads/{uploadId} 已鉴权请求、诊断 ZIP、包 SHA-256；ZIP 内有上述 manifest 服务端校验通过，包与索引持久保存，返回接收回执
GET /api/diagnostics/thread-uploads/{uploadId} 同一身份边界下查询上传 ID 返回已接收回执、处理中或失败状态；不存在明确返回未接收
GET /api/diagnostics/{diagnosticId} 有权限的用户或运维请求 返回只读诊断摘要、run／checkpoint 时间线、附件与缺失项

接口基于现有账号、租户／组织和设备身份鉴权；服务端不相信 manifest 中自报的用户或租户。幂等键为鉴权范围内的 uploadId，同时绑定来源安装标识、thread ID 和包摘要。同 ID 同摘要重试返回同一回执；同 ID 不同摘要返回冲突，不覆盖已接收材料。

服务端先将上传流写入隔离暂存区，限制压缩与解压大小、文件数量和路径；拒绝路径穿越、符号链接、重复路径、未知格式版本及摘要不符。确认包只对应一个业务 thread，run 映射、checkpoint 父关系与缺失声明互相一致。超出配置上限时返回明确错误，客户端展示限制，不能悄悄丢数据后宣称完整上传。

只有包已持久保存、元数据与可查询索引已提交，才返回“已接收”。 回执至少包含 uploadId、diagnosticId、threadId、bundleSha256、服务端 receivedAt，以及材料完整性和缺失列表。若服务端采用异步校验，202 仅表示处理中，客户端继续查询，不能当成最终接收成功。

运维接收页按诊断编号、来源设备、thread、run 和状态查找；详情将消息、工具事件、checkpoint 与运行快照关联呈现。服务端诊断存储与生产任务的可执行 checkpointer 隔离：不覆盖已有生产 thread，不连接包中的 MCP，不加载 Skill 脚本，不调用 invoke／stream／resume。查看与下载均校验权限，材料保留期限与删除遵循服务端策略。

服务端配合

  • 提供鉴权后的诊断上传、幂等查询、只读检索和附件下载；普通用户可提交自己有权查看的 thread，运维查看范围由服务端授权。
  • 提供可查询的包大小、展开大小、文件数和格式版本限制；校验失败返回稳定错误类别，客户端不依赖原始堆栈或数据库错误文本。
  • 将包、摘要、来源、run／checkpoint 索引和接收回执一起纳入持久接收流程；未提交完成的暂存数据不出现在已接收列表。
  • 存储接收身份与时间，并使用平台既有访问审计和保留策略；上传业务记录、任务结果确认、生产调度状态彼此独立。

本章新增的是持久化诊断业务记录，不新增日志平台、span 或指标。上传 ID、状态、稳定错误类别和服务端回执已覆盖首版排查与验收需要；用户消息、checkpoint 内容、工具正文和凭据不写入遥测。若后续增加上传成功率、耗时等监控，另按项目规范确认统计口径。

验收边界

  1. macOS ARM64 与 Windows x64 均验证 SQLite 落盘、重启可读、异常退出后已提交 checkpoint 保留；原生 SQLite 依赖随正确架构的包交付。
  2. 两个 thread 同时存在时，只导出所选 thread；覆盖多 run、根／子图 namespace、父链、pending writes 与版本匹配。
  3. 正在执行时不能取得半写入快照；停止、超时、崩溃、SQLite 损坏和磁盘写满均有明确结果，未提交部分不冒充已保存。
  4. 覆盖凭据嵌入在消息、工具输出、metadata 与 checkpoint 中的情况；默认无浏览器登录态和其他会话材料。
  5. 服务端真实接收测试覆盖持久保存后回执、丢失回执后的幂等重试、同 ID 不同摘要、越权、超限与恶意压缩路径。
  6. 接收后可按诊断编号查到同一 thread 的 run／checkpoint；查看包不会产生模型、MCP 或浏览器调用。
  7. 旧版无 checkpoint、附件缺失与脱敏包能展示真实完整性；客户端导出成功、HTTP 请求完成和服务端已接收三者不混淆。

10 · 服务端 API：客户端接入所需的最小契约

串讲重点：服务端提供身份与权限、官方物料、草稿与发布、远端任务通道、桌面更新和诊断接收；每项接口都明确何时才算成功，以及断线后怎样查询或重试。

本章是拟定的接入契约，相关平台 API 和 WebSocket 通道尚未实现。 路径名称可适配现有平台网关，输入输出与成功边界保持一致；不据此另建账号体系、审批平台或文件级发布服务。客户端已实现的本地能力见第 08 章。

统一契约

业务 API 使用 HTTPS /api/…，JSON 使用 UTF-8，时间为带时区的 RFC 3339；业务 JSON 请求体、成功响应和 WebSocket 报文携带 schemaVersion: 1，不支持的版本明确拒绝。GET 请求无需 JSON 请求体；二进制上传在 manifest 声明版本，二进制下载与 Tauri 更新清单遵循各自格式，不套 JSON 业务响应。

  • 复用现有 Bearer Token 或平台既有安全会话机制；服务端从已验证凭据确定用户、组织和权限，不相信请求正文自报的身份。下载 URL 与诊断附件同样需要授权，可使用短时有效的受限下载地址。
  • 普通用户读取有权使用的官方版本、执行自己的任务并提交自己的诊断；运维人员维护官方草稿和发布。仅在前端隐藏按钮不能代替服务端权限检查。
  • 列表请求使用 cursor、limit，服务端限制最大页长；返回 items、nextCursor。游标包含固定列表修订，列表变化使旧游标失效时明确要求重新读取，不能静默漏项。详情与单次发布不分页。
  • 创建草稿修订、正式发布等写请求携带 Idempotency-Key。同一鉴权范围、操作和键绑定请求内容：相同内容返回原结果，内容不同返回 409 idempotency-conflict。超时后用同一键重试；不能换键猜测上次是否成功。
  • 修改草稿头、提交发布时携带读取到的 expectedRevision／expectedContentId；服务端发现基线变化返回冲突，客户端重新展示差异。已经保存的修订、正式包和发布标签不原地覆盖。
  • 失败返回安全的 { error: { code, message, requestId, details? } }；details 仅给出可处理的字段或资源标识，不含 Token、原始请求头或内部错误来源链。网络超时不等于服务端未写入。

Skill 清单逐项列出 POSIX 相对 path、kind，文件另有 bytes 与 sha256，空目录也保留。完整包内容摘要严格采用Skill 版本文件布局的规范化算法；传输 ZIP 的 SHA-256 与包 contentId 是两个值，不能混用。服务端提供跨语言摘要用例供客户端对照。

正式内容保持 skills/releases/<skillId>/<contentId>/ 的包内结构；人工标签和上传者等元数据在包外。下载在临时目录完成，拒绝路径穿越、符号链接、重复路径、大小写冲突及超限内容，客户端重算摘要后原子提交缓存。失效 URL 可重新取得，但同一内容 ID 对应的内容不能改变。

客户端只请求当前装配缺少的包；已缓存相同完整版本可复用。新会话核对版本，已有会话继续使用固定快照。清单、权限、下载或摘要任一失败都停止本次准备，不回退旧版或移除缺失能力后继续执行。

发布请求提交即表示运维确认，不加审批或强制实验门槛。旧标签和历史装配保持不可变；仅修改模型参数不发布 Agent。发布超时使用原幂等键重试获取同一发布结果，不能因重试再生成一轮标签或新发布。

WebSocket：调用、取消、结果和确认

客户端以现有身份连接 WSS /api/clients/connect。握手校验用户、组织及安装身份，连接归属不能由正文任意指定；凭据不放 URL 查询串。首帧协商 schemaVersion、clientInstallationId、桌面版本和支持的 builtinTool ID，服务端确认连接可用后再投递任务。

每条业务消息包含 schemaVersion、type、messageId、callId（连接级消息除外）与 payload。messageId 标识一次投递，callId 标识一次业务执行；重投可以有新消息 ID，但不能改变调用内容。每个 Agent 的业务 input／result schema 由该 Agent 对应的服务端业务单独定义。

消息 方向 最少业务字段与含义
task.call 服务端 → 客户端 callId、指定客户端、agentId、agentContentId、input、context、调用有效期；调用确定官方版本，不调用本地私有 Agent
task.accepted 客户端 → 服务端 callId、threadId、runId、接收时间；去重记录落盘且取得本轮执行名额后发送，只表示受理
task.status 客户端 → 服务端 callId、单调递增 sequence、准备／执行／停止中状态；用于状态展示，不以它代替最终结果
task.cancel 服务端 → 客户端 原 callId、取消请求 ID；只针对这次调用，不取消其他任务
task.cancelled-receipt 客户端 → 服务端 取消请求 ID、stopping／already-finished／not-found；收到取消不等于工具已停止
task.result 客户端 → 服务端 callId、稳定 resultId、结果摘要、终态、结果或安全错误类别、起止时间、运行快照；如未开始则说明无 run／快照
task.result-ack 服务端 → 客户端 callId、resultId、同一结果摘要、服务端接收时间；结果与索引已持久提交才确认

调用去重与忙时处理

客户端在鉴权范围和安装身份内持久记录 callId 与不可变调用内容，先检查重复，再争用执行名额。重复投递同一调用时，只返回已知受理状态或原结果，不开始第二次模型、MCP 或 Chrome 操作；同 ID 不同内容明确拒绝为 call-conflict。

新调用只创建一个独立的客户端 thread／run。本地、实验与远端任务共用同一名额，准备和停止排空期间也占用；忙时保存并返回 busy，不进入客户端队列。服务端如决定重试执行，使用新 callId；重新发送已返回忙的旧 ID 仍得到原拒绝结果。

去重记录不能在服务端仍可能重投时提前清理；清理期限覆盖约定的最大重投窗口，过期调用明确拒绝，不能当成新任务。过期、权限不足、版本不匹配和准备失败均有明确结果，不用“收到消息”代替成功执行。

终态、结果补传与取消

执行终态区分 completed、failed、cancelled、timed-out、interrupted-unknown；未受理调用另返回 busy 等拒绝类别。终态和结果交付状态分别保存，运行结束先落盘，再发送结果。结果包含实际 Agent／Skill、启用工具／MCP、桌面版本及模型参数，排除凭据。

服务端按鉴权范围、安装身份、callId 和 resultId 幂等接收；相同结果重复发送返回同一 ACK，不重复驱动后续调度，同 ID 不同摘要返回冲突。客户端核对 ID 与摘要后才记为已交付，普通 WebSocket 发送成功或连接心跳不能充当结果 ACK。

  • 网络断开但进程仍在：当前任务继续，客户端有界退避重连；重新鉴权完成后补传未 ACK 的原结果，不重新执行。
  • 重启发现已完成结果：恢复交付，复用原 resultId 和摘要；不重新装配 Agent。
  • 重启发现未完成任务：保存并回传 interrupted-unknown，不自动续跑或重试。SQLite checkpoint 仅提供诊断证据，不改变该规则。
  • 收到取消或到达客户端兜底超时：停止后续步骤，等已发起操作排空后保存终态；取消回执与最终结果分开。任务已结束时返回原结果，不能改写终态。
  • 遇到人工登录／验证：本轮失败，用户在专用浏览器处理后新发起调用。已执行的外部操作不回滚，也不承诺外部副作用恰好发生一次。

正常任务通道不发送逐条模型正文、完整工具过程、SQLite 数据库或 checkpoint。需要这些材料时使用第 09 章的显式诊断上传；结果 ACK 与诊断接收回执互不替代。

桌面更新：静态站点即可

沿用第 05 章，内网 HTTPS 静态站点提供 GET /updates/stable/latest.json 和不可变版本下载地址，不要求业务登录。它使用 Tauri updater 的原生格式，不包裹业务响应：

{
  "version": "0.2.0",
  "notes": "本版更新说明",
  "pub_date": "2026-10-19T08:00:00Z",
  "platforms": {
    "darwin-aarch64": {
      "url": "https://updates.example.invalid/0.2.0/omniops-bots.app.tar.gz",
      "signature": "构建产物 .sig 文件的完整内容"
    },
    "windows-x86_64": {
      "url": "https://updates.example.invalid/0.2.0/omniops-bots-setup.exe",
      "signature": "构建产物 .sig 文件的完整内容"
    }
  }
}

示例域名和签名需由交付配置替换。version 使用有效 SemVer，不能使用资产标签 v.1.0.0；signature 是签名正文，不是签名下载 URL。macOS 使用更新专用 .app.tar.gz，Windows 使用选定的已签名 NSIS EXE 或 MSI；签名与 URL 必须对应同一份产物。Tauri 官方 updater 契约规定了这些字段与平台键。

先上传并验证两个平台产物，再原子更新 latest.json；同版本产物、URL 和签名不变。签名私钥只在受控构建流程中，站点仅分发产物；客户端内置公钥。前端、Tauri、Node、CEF／内置浏览器和 Playwright 等随包运行时一起更新，不靠 Skill 同步安装浏览器工具。

无更高版本时客户端保持当前版；下载成功仍需用户确认并重新检查空闲才能安装。本期没有强制更新、静默安装、差分或自动回滚。实际 updater 接入、签名配置及两平台旧版升级验收仍待实施。

GET /api/diagnostics/{diagnosticId}/attachments/{attachmentId} 有权限的附件 ID，不能传任意磁盘路径 校验归属后返回附件字节或短时受限下载地址；浏览器下载不执行附件代码

幂等身份沿用 uploadId，绑定来源安装、thread 与包摘要；同 ID 同包返回同一回执，不同包返回冲突。回执至少有 uploadId、diagnosticId、threadId、bundleSha256、receivedAt、完整性和缺失清单。没有包及可查询索引的持久提交，不能返回“已接收”。

客户端 SQLite 只导出所选 thread 关联的 run、全部 namespace、checkpoint 依赖和 pending writes；服务端接收逻辑归档，不接收全库、WAL／SHM 或浏览器登录态。校验归属、摘要、格式版本、路径及压缩／解压上限，保留可理解的缺失和脱敏说明。

诊断存储与生产可执行 checkpointer 隔离，查看或下载不触发模型、MCP、Playwright，也不 invoke／stream／resume 原任务。附件权限、保留期限与删除按现有服务端策略执行。

联调验收与交付边界

  1. 用普通用户、运维和越权身份验证清单读取、草稿写入、发布、任务连接及诊断下载；前端隐藏操作不影响服务端权限判断。
  2. 同一完整 Skill 包在两端得到相同内容 ID，目录与原始字节不变；缺包、损坏、过期下载地址及半包均不进入运行。
  3. 覆盖草稿重试、并发发布、标签冲突和 Skill／Agent 联动失败，确认无部分发布；超时后原幂等键得到同一结果。
  4. 覆盖调用重复、同 ID 不同内容、忙时拒绝、取消竞争、丢失结果 ACK、断线和重启；不重复执行，不重复推进服务端后续调度。
  5. 两个平台验证正确 updater 清单、真实签名产物与旧版升级；错误包不安装，任务期间不退出。
  6. 上传真实的指定 thread 诊断包，验证持久接收、回执幂等、权限、材料缺失和附件下载；浏览诊断不产生执行副作用。

首版使用持久化的修订、发布结果、调用状态、交付确认和诊断回执完成排查，不新增日志平台、span 或指标。后续确需遥测时再确认字段与统计口径；用户正文、checkpoint 和浏览器凭据不作为遥测材料。
