# 00 客户端总体设计

**客户端是运行在用户本机的后台 Agent 执行端，由服务端 Agent 以任务的形式调用。线上用户的主体操作在服务端 Console 完成。** 用户在 Console 发起业务请求、查看任务状态和结果；服务端 Agent 负责业务编排，将需要本机能力的任务交给客户端 Agent，客户端在本机执行并回传结果，供服务端 Agent 继续处理并在 Console 呈现。

**线上日常使用主线是：用户操作 Console → 服务端 Agent 编排并下发任务 → 客户端 Agent 后台执行 → 结果回传服务端 → Console 展示。** 客户端通常作为后台进程运行，线上用户只看到连接状态等基础信息，不展示会话、资源编辑、执行过程和浏览器工作台组成的调试桌面；任务执行不以打开该调试桌面为前提。

**运维调试与物料迭代是另一条工作主线：发现问题 → 在调试桌面编辑 → 本地实验与修正 → 运维本人确认 → 上传发布版本 → 新任务使用并反馈。** 运维人员在调试桌面修改 Skill、补充文件、调整 Agent 提示词与装配，直接选择 Agent 本地试跑并检查过程，自己确认可用后上传发布。未上传的编辑也能实验，上传保存草稿与正式发布是两个动作，发布提交即表示运维本人已经确认。

两种使用方式复用本地 Node.js／LangGraph 执行能力，经 **Playwright 操作应用管理的外部 Google Chrome** 完成任务。调试工作台另保留独立的内嵌 CEF 运维浏览器，供运维人员手动操作。

**我们的核心资产是受版本控制、可持续演进的 Agent 提示词与 Skill。** 提示词沉淀任务目标、操作边界和结果要求，Skill 完整文件包沉淀可复用的运维方法、操作步骤和参考资料。团队按周将实际任务中的反馈转化为改进，经本地编辑、按需实验后发布新的确定版本，逐步提高 Agent 的任务完成能力。

本设计分别说明线上后台执行与运维调试、资源管理、运行恢复；后续章节中的资源页面、本地会话和工作台描述均属于运维调试视图，不能据此把完整调试桌面作为线上用户界面。服务端 Console 和服务端 Agent 是外部接入方，各章最后列出客户端需要其配合提供的能力。上述线上流程是目标使用方式，服务端远端任务接入及面向线上用户的界面收敛仍待完成，不能以当前调试桌面已实现来代替。

线上客户端只提供连接状态等基础信息，连接状态区分已连接、重连中和离线；用户日常在服务端 Console 操作，无需进入本地调试界面。运维调试桌面由左侧导航、中央内容区和右侧工作台组成：导航组织会话、Agent 与 Skill，中央区域承载编辑和对话，工作台展示浏览器与执行过程，账号区域展示用户身份与运维权限。

1. 作为线上用户，我希望在服务端 Console 发起业务请求、查看任务状态和结果，由服务端 Agent 调用本机 Agent 完成所需操作。
2. 作为线上用户，我希望客户端平时作为后台进程运行，仅在需要时查看连接状态等基础信息，无需操作调试桌面。
3. 作为服务端 Agent，我希望以任务形式调用客户端的官方 Agent，取得状态与最终结果，并在客户端断线后仍能收到已有结果。
4. 作为运维人员，我希望发现任务中的不足后，在调试桌面修改 Skill 文件或 Agent 提示词，选 Agent 试跑、查看过程与结果并继续调整；自己确认后上传发布，让后续线上任务使用确定版本。
5. 作为运维人员，我希望能在调试时查看独立 Chrome 窗口与本地执行记录，并按需上传指定 thread 的诊断材料，取得服务端确认接收的编号。

## 简要设计

客户端的后台执行能力与运维调试视图复用同一套 runtime：线上任务由服务端 Agent 下发，客户端准备所需物料，在专用 Chrome 中执行，并保存可补传的结果；运维人员通过调试桌面编辑、实验和检查过程。线上基础状态界面与调试桌面分别服务于这两种使用场景。Tauri 承担桌面包装，本次不引入其他 Rust 业务模块作为前置条件。

### 线上用户的一次任务

用户在服务端 Console 提出巡检请求，服务端 Agent 编排业务步骤，并以独立任务调用客户端官方 Agent，选择确定版本的 AgentCard，传入稳定 messageId 和显式任务上下文。客户端在后台核对物料、固定快照并执行本机操作，将 Task 状态、最终 Artifact 和非敏感运行摘要交付；服务端确认接收后，由服务端 Agent 继续后续业务，Console 向用户展示任务状态和结果。普通任务交付不持续上传逐条模型输出，本地过程记录供运维调试和诊断使用。

客户端不要求用户打开调试桌面或在本地选择 Agent、输入任务。需要人工登录或验证时，按执行章节处理并显式发起新任务，不自动续跑；具体业务操作与结果查看仍在 Console 完成。

### 运维人员的一次物料改进

例如，运维人员发现一次巡检遗漏了新的页面检查项，就在客户端打开对应 Skill 的官方草稿工作副本，补充操作步骤和参考文件，再勾选现有 Agent 作为模板实验。实验直接使用当前完整内容，在外部 Chrome 中执行；运维人员对照过程与结果继续修改，原 Agent 和已发布 Skill 保持不变。

| 工作步骤 | 运维在客户端做什么 | 得到什么 |
| --- | --- | --- |
| 就地编辑 | 修改 `SKILL.md`、上传或替换包内文件，按需调整 Agent 提示词与装配 | 可继续编辑的本地内容或官方草稿，无须每改一个文件就上传服务端 |
| 快速实验 | 在 Skill 页面勾选 Agent，发起独立实验；结合结果继续改、再试 | 每次实验固定完整快照，过程与产物可查看；未上传的内容也能试跑 |
| 本人确认 | 运维确认这次内容可用于正式任务，选择本次发布范围并手填标签 | 明确要上传发布的完整内容；不增加审核人或强制实验通过门槛 |
| 上传发布 | 上传确定的完整草稿修订并提交正式发布；已上传且未变化的修订可直接使用 | 服务端校验权限与标签，保存不可变版本；Skill 与受影响 Agent 的新标签一次联动发布 |
| 使用与反馈 | 新会话同步并装配所选版本，从实际任务中发现下一次改进 | 团队复用已确认的运维方法，旧会话沿用原快照，历史版本保留 |

周内可以反复编辑与实验，也可以按需上传保存草稿；**只有运维明确提交正式发布，改进才成为可供团队同步使用的官方版本。** 团队按周汇总已确认的改进发布，上传本身不增加审批环节。客户端负责把迭代做得便捷，服务端负责把已确认版本保存完整、分发准确。

| 客户端能力 | 主要行为 | 服务端需配合 |
| --- | --- | --- |
| 线上基础状态 | 后台保持任务连接，仅向线上用户展示连接状态等基础信息 | 提供连接鉴权与状态确认，Console 承载业务操作及任务结果 |
| 运维资源管理 | 在调试桌面修改 Skill 文件与 Agent 提示词、装配，反复本地实验，运维确认后上传发布 | 校验身份权限，保存完整草稿修订与不可变发布版本，分发已确认物料 |
| [Provider 配置](./11-Provider.md) | 本地管理多个 OpenAI Chat Completions 兼容接入地址及模型，选择默认项、手动测试连接，Key 存系统凭据库 | 本期不下发 Provider 配置或 Key，不新增平台 API |
| 同步装配 | 核对版本、按需下载、保留历史包、固定运行快照 | 通过 HTTPS 提供版本清单与物料 |
| 浏览器执行底座 | 随包提供 Playwright，按需启动本机 Google Chrome，按会话绑定独立页面并保留专用登录态 | 通过任务协议调用客户端；浏览器与网站登录态保留在本机 |
| 任务执行 | 线上接收服务端 Agent 的任务调用；运维可在调试桌面手动试跑，均经 builtinTool 和 Playwright 在外部 Chrome 中执行 | 服务端 Agent 使用标准 A2A 消息与取消操作，WSS 仅负责网络传输 |
| 结果交付 | 本地保存状态、结果与快照，断线后补传；逐条过程仅供运维调试查看 | 接收 Task 状态、最终结果与必要运行摘要，持久保存后确认，服务端 Agent 继续编排，Console 展示任务状态与结果 |
| 桌面更新 | 检查、下载、验签，在空闲时由用户确认安装 | 提供更新清单和已签名整包下载 |
| 运维诊断 | 将指定 thread 的 SQLite checkpoint、运行快照与记录导出，经预览后上传 | 校验并持久保存诊断包，返回回执，提供只读排查入口 |

客户端保留未同步编辑、已下载历史版本、会话快照与执行记录。运维调试时可自由编辑本地资源；官方已发布资源同步后只读，服务端只调用官方 Agent。线上任务按调用指定版本自动准备物料，不要求线上用户进入资源管理页。

Provider 配置是客户端运行条件：允许自定义 base URL，手动维护上游模型名；新会话可使用全局默认 Provider 与模型或在开始前改选，开始后固定，不可用时明确报错，不自动切换。多 Provider 管理、连接测试与系统凭据存储已接入；macOS 凭据存储已验证，Windows 实机验收待完成，详见 [11 · Provider](./11-Provider.md)。

### Agent 外部 Chrome 与手动运维 CEF

**线上目标链路：用户操作服务端 Console → 服务端 Agent → WSS 传输 → A2A 协议与任务处理 → 客户端 Node.js／LangGraph Agent → builtinTool → Playwright／本地 CDP → 外部 Chrome 的固定页面；执行结果按任务回传服务端 Agent，再由 Console 呈现。** 服务端调用属于待接入能力，不经过用户手动操作调试桌面。

**当前运维本地调试链路：调试桌面输入任务 → Tauri adapter／IPC → Node.js／LangGraph Agent → 同一套本机工具与 Chrome 执行能力。** Agent 的页面在独立 Chrome 窗口中显示；调试工作台的 Chrome 标签展示状态并提供「显示 Chrome」。后台运行描述的是客户端的日常使用方式，不要求 Google Chrome 采用无界面模式。

| 组成 | 职责 |
| --- | --- |
| 服务端 Console 与 Agent（外部系统） | Console 承载线上用户操作；服务端 Agent 编排业务，以任务调用客户端 Agent 并消费结果 |
| Tauri 界面 | 线上展示连接等基础状态；运维调试桌面管理 Agent、Skill、会话与执行记录，通过 adapter 调用 Node 后端 |
| 本地 Node.js／LangGraph runtime | 在后台执行服务端任务或运维调试任务，装配固定快照、调用模型与工具，管理并发运行、停止、超时及 Chrome 生命周期 |
| Playwright | 连接本次 thread 指定的 CDP target，执行检查与脚本；目标不匹配时结束操作 |
| 外部 Google Chrome | 使用应用专用 profile 保存登录态，各 thread 绑定独立页面；用户可在真实 Chrome 窗口中操作 |
| 内嵌运维 CEF | 固定手动页面 `__manual__`；独立的地址、历史、布局和输入，由运维人员操作，Agent 工具不接入 |

Node.js、Playwright 和 CEF 随桌面整包交付；Google Chrome 需单独安装，其更新由 Chrome 自身管理。普通会话切换只选择状态，不启动或抢焦点；浏览器工具首次执行或用户显式「显示 Chrome」才按需创建页面。应用更新范围见第 05 章。

页面检查、脚本保存与执行都在本机完成。脚本执行时保存源码快照并核对内容摘要，产物关联执行记录；脚本始终沿用该轮绑定的 Chrome 页面。工作台的浏览器入口相互独立，运维 CEF 导航和输入不占用 Agent 的任务页面；Agent 工具调用不会切走当前运维标签或清除地址草稿。对 Agent 当前 Chrome 页面的人为操作需由使用者协调，应用不将任务锁扩展到外部 Chrome 的原生输入。遇到人工登录或验证，本轮结束；用户处理后显式发起新一轮。停止不回滚外部操作，也不自动续跑。

**脚本截图来自本轮绑定的外部 Chrome 页面。** `run_playwright_script` 在结束时尝试保存当前视口为 `screenshot.png`，普通脚本报错也会尝试保存；取消、超时或浏览器崩溃可能导致截图缺失。截图关联该次脚本产物，不改拍运维 CEF，也不作为未发生操作的证据。

专用 profile 与用户日常浏览器隔离，网站 Cookie、登录态及本地 CDP 地址不作为服务端任务材料上传。故障时按第 09 章导出指定 thread 的脱敏证据，不上传整个浏览器 profile。

当前本地链路的代码依据：[浏览器连接](../../desktop/runtime/browser/browser.ts)、[页面匹配](../../desktop/runtime/browser/browser-target.ts)、[脚本执行](../../desktop/runtime/browser/script-workspace.ts)、[macOS 原生视图](../../crates/omniops-bots-desktop/src/native_browser.rs)与 [Windows 原生视图](../../crates/omniops-bots-desktop/src/native_browser_windows.rs)。服务端远端调用仍为待接入能力，接口汇总见[服务端 API](./10-服务端API.md)。

### 核心资产如何积累与演进

| 对象 | 沉淀内容 | 版本与演进方式 |
| --- | --- | --- |
| Agent 提示词 | 角色、目标、操作边界、决策要求与输出要求 | 作为 Agent 装配的一部分保存；正式修改生成新的 Agent 内容 ID 和人工发布标签，不另建一套提示词发布体系 |
| Skill 完整包 | `SKILL.md`、操作说明、引用资料、脚本及随包资源 | 完整包生成内容 ID；已发布包不可变，新版本保留旧包，Agent 明确引用所需版本 |
| Agent 装配清单 | 提示词、固定 Skill 版本、builtinTool 选择和 MCP 配置 | 将核心资产组合为可运行的 Agent；装配变化生成新 ID，并手填 `v.1.0.0` 形式的标签 |
| 运行快照与执行记录 | 本次使用的装配、运行条件、过程与结果 | 为问题定位和下一轮改进提供依据；快照不建立发布版本，实验产物不混入 Skill 包 |

客户端提供核心资产的编辑、实验与使用入口；服务端统一保存官方草稿修订和不可变发布历史。提示词只改目标或行为要求时，可以复用原有 Skill 版本；Skill 正式发布时，一并更新受影响 Agent 的引用与内容 ID，并由运维手填各自的新标签。保存草稿不触发联动发布。

MCP 提供远端执行能力，配置随 Agent 同步；MCP 服务本身不进入本项目版本体系。builtinTool 提供桌面执行能力，实现随桌面应用更新。每周改进提示词和 Skill 不要求同时发布桌面端；只有确需新的内置能力时才安排桌面更新。

### 按周迭代发布

| 阶段 | 运维在客户端完成的工作 | 形成的结果 |
| --- | --- | --- |
| 周内迭代 | 结合实际任务结果定位不足，修改 Agent 提示词或 Skill 草稿，按需选 Agent 实验 | 可继续修改的草稿、独立保存的实验记录；未完成内容留在草稿中 |
| 每周发布 | 选择本周本人已确认的改进，上传确定的完整修订，手填本次 Skill 与受影响 Agent 的新标签，提交正式发布 | 一次确定的资产更新；只改提示词则发布 Agent，Skill 改动则联动发布受影响 Agent；无变化的物料继续复用 |
| 发布后使用与反馈 | 新会话核对并装配所选新版，观察执行结果，把新问题纳入下一周 | 旧会话保持原快照，发布历史可追溯，改进持续积累 |

按周发布是团队的迭代节奏，不增加审核人、审批流或强制实验门槛；运维提交即表示本人已确认。标签始终人工输入，周次和日期不替代发布标签，也不自动覆盖历史版本。没有已确认变更时不创建空版本。

## 客户端

### 安装包包含什么

**客户端整包交付运行底座、本地执行代码和运维界面；正式业务能力按确定 Agent／Skill 版本同步。** 服务端复杂 graph 的节点、路由和业务状态留在服务端应用中，通过 A2A 调用桌面；客户端随包带有自己的本地执行图与工具实现，接到任务后装配所选版本并执行。

| 随安装包交付 | 具体内容 | 更新方式 |
| --- | --- | --- |
| 桌面壳与前端 | Tauri 原生程序、已构建的 React 页面、IPC 与系统能力、Node 子进程及浏览器进程生命周期管理 | 随客户端整包更新；终端用户不需要安装 Rust 或前端开发环境 |
| 私有 Node.js 与业务 runtime | 固定 Node.js `26.11.1` 可执行文件、`desktop/runtime/` 的生产模块；包括装配、本地 LangGraph 执行图、builtinTool、模型／MCP 调用、Chrome 管理和本地持久化代码 | 随客户端整包更新；使用随包 Node，无须用户另装 Node／npm |
| 生产依赖与原生组件 | LangGraph.js、Deep Agents、LangChain、MCP SDK、`playwright-core`、SQLite checkpoint 依赖及匹配平台的原生 SQLite addon | 按锁文件构建并随包交付，不在用户机器上现场安装依赖；runtime 源码排除本仓测试、fixture 与开发桥接 |
| 内嵌运维浏览器 | CEF 运行库、资源、语言文件及对应平台的 helper／启动组件 | 随客户端整包更新；供手动运维浏览器使用，Agent 自动化使用外部 Chrome |
| 交付清单与许可 | `runtime-manifest.json`、第三方许可与声明，记录随包 runtime 的版本、目标平台和校验信息 | 与本次整包一致，不代替 Agent／Skill 的业务内容版本 |

当前打包入口覆盖 macOS arm64 的 `.app`／`.dmg` 和 Windows x64 的 NSIS 安装器。包内本地执行图和 builtinTool 属于应用代码，修改这些实现需要发布客户端；它们不作为 Agent／Skill 资产发布。A2AService 已随 Node runtime 提供并完成独立模块验证，共用同一 runtime；**生产 WSS 与桌面入口组装待接入，现有打包配置不表示 A2A 链路已经上线。**

| 本机运行数据 | 安装包外的应用数据目录、资源目录及选定工作目录：本地草稿、已下载版本、运行快照、工作文件、脚本、Artifact、会话历史与 SQLite checkpoint | 执行时生成或保存，不写回只读安装资源；整包升级保留，不能据此自动续跑中断任务 |

| 模型、MCP 服务与凭据 | runtime 使用配置的外部模型和 MCP 服务；Provider／模型配置在本机维护，凭据使用系统凭据库，普通配置只保存引用 | 包内包含调用 SDK，不包含模型权重、远端服务实现或真实密钥；服务端复杂 graph、PostgreSQL、Redis 和共享文件服务也不安装到客户端 |

### 客户端运行职责

- 面向线上用户展示连接状态等基础信息，日常作为后台进程运行；复用已有 Token 连接服务端，WebSocket 断线后退避重连。任务接收、执行与交付不依赖打开调试桌面。
- 运维调试桌面展示身份与权限，提供 Skill 文件编辑与上传、Agent 提示词及装配调整、选 Agent 实验的连贯入口；未上传内容也能反复实验，官方已发布配置只读。
- 围绕提示词和 Skill 的每周改进保存草稿、实验记录及发布引用，展示本次 Agent 实际装配；发布过程不增加审批。
- 新会话同步清单，按需下载缺失物料；调用前核对版本，失败不拿旧版代替。
- 运行前固定装配快照，检查所需内置工具；Playwright 按会话绑定外部 Chrome 的指定页面，不同会话可并发；同会话已有运行、其页面正在手动导航或并发容量已满时返回忙。
- 运维在调试桌面的「设置 → 偏好设置」修改「并发任务上限」，默认 4，支持 1～64 的整数；保存到本机后立即用于新任务受理，无需重启，下调不取消当前任务，详见[任务执行与恢复](./07-任务执行与恢复.md)。
- 后台保存结果并补传，正常任务交付只向服务端发送 Task 状态、最终结果和非敏感运行摘要；线上用户在 Console 查看任务状态和结果，逐条过程保留在本地供运维调试查看。
- 需要排查时另行按指定 thread，通过 HTTPS 上传脱敏后的 SQLite checkpoint、过程与关联材料。服务端确认接收后展示诊断编号，具体见[运维与诊断上传](./09-运维与诊断上传.md)。

### 展望：录制模式，将一次告警处理沉淀为 Skill

**后续方向，本期不实现。** 运维人员在客户端主动开启录制模式，选择应用管理的外部 Google Chrome 页面，人工完成一次告警排查与处理。客户端按操作顺序记录导航、点击、输入、选择等动作及关键页面结果，保存为本次告警的本地录制草稿；运维可补充告警背景、每一步的目的、判断依据和最终处理结果，让一次真实操作成为可整理、可复用的 Skill 素材。

**预期闭环：开始录制 → 人工处理告警 → 停止并保存 → 预览整理 → 回传到目标 Skill 草稿 → 确认发布新版本。**

| 阶段 | 客户端预留的能力 | 形成的材料 |
| --- | --- | --- |
| 开始录制 | 显式选择本次 Chrome 页面和关联告警，显示录制状态；只记录本次选择的范围 | 一次独立录制的业务背景与操作范围，不混入其他 Task 或手动 CEF 的操作 |
| 人工处理与保存 | 保存有顺序的操作步骤与关键结果，允许补充说明、停止或放弃；人工操作与 Agent 自动执行分开使用 | 本地录制草稿；是否处理成功由实际验证结果说明，录制完成本身不代表告警解决 |
| 预览与整理 | 上传前查看、删减和脱敏；密码、Token、Cookie 不进入回传材料，业务输入按需改成参数占位 | 可复用的步骤、前置条件、判断与验证方法；保留必要来源，去掉与复用无关的数据 |
| 回传到 Skill | 选择已有 Skill 的可编辑草稿，或创建新的 Skill 草稿，复用既有完整草稿修订上传流程 | 在 `references/` 中沉淀告警处理实践，并由 `SKILL.md` 索引；稳定步骤按需提炼为 `scripts/`，不自动把原始录制当作可执行脚本 |
| 确认发布与使用 | 运维继续编辑、按需实验，确认后按原流程发布完整 Skill 新版本，更新受影响 Agent 的固定引用 | 后续任务复用已确认的方法；已发布包和正在执行的只读快照保持原版本 |

录制草稿独立保存在安装包外，回传属于运维主动维护 Skill 的流程，不随普通 A2A Task 结果自动上传，也不直接覆盖已发布 Skill。已有本地副本在回传失败时保留，便于修正后继续上传；原始记录只作为候选素材，正式内容沿用本人确认发布的规则。录制不自动重放告警处置，也不恢复或重跑已经终态的 Task。

本节只预留产品方向，录制实现、文件格式与观测设计留待落地时细化；不新增录制 API、A2A 私有消息、日志、span 或指标。素材的整理方式衔接[核心 · Skill 模板与迭代](./核心-Skill模板与迭代.md#如何从任务反馈迭代到正式版本)，草稿与正式发布沿用[第 01 章](./01-SKILL.md)。

## 详细设计

以下运行模型按消息发生顺序描述客户端行为；各图是独立场景。准备失败、忙或执行中断的路径分别见同步与执行章节。

### 场景一：线上客户端后台接收服务端 Agent 任务

前提：线上用户已在服务端 Console 发起业务请求，服务端 Agent 编排到需要本机能力的步骤，以任务形式调用客户端官方 Agent。客户端已连接，指定版本准备成功且并发容量可用；新会话绑定独立页面，不要求用户打开调试桌面。

![A2A 任务受理、客户端后台执行与持久交付](./assets/a2a/run.svg)

[打开 A2A 运行顺序图](./diagrams/a2a/run.html) · [核心章节：完整场景与协议分工](./核心-服务端通过WS调用客户端.md)

结果：客户端在后台为每次调用新建独立、只读会话，逐条过程保留在本地供运维调试查看；线上用户在 Console 查看任务状态和结果。结果与快照先落本地，再以标准 Task／Artifact 向服务端交付，持久确认前保留，服务端 Agent 幂等消费结果后继续编排。断线继续执行，重连只补传；重启后未完成任务报告“执行中断、结果未知”。本场景是线上日常使用主线，远端接入仍待实现。

### 场景二：运维快速迭代，确认后上传发布

前提：运维从实际任务反馈中发现一项 Skill 改进需求，在客户端编辑工作副本。图中展示选择 Agent 做本地实验、本人确认后手填标签并上传发布的过程；实验结果不满足预期时，继续在本地修改并发起新实验，直到运维决定发布。实验按需进行，不是发布审批门槛。

![运维物料迭代：客户端编辑与实验、本人确认、上传发布与新版使用](./assets/runtime/00-weekly-evolution.svg)

[打开顺序图：运维迭代与确认发布](./diagrams/runtime/00-weekly-evolution.html)

图中的“按需保存完整草稿修订”只保存编辑进度，不发布、不联动 Agent；这一步也可以在本地实验之后进行。正式发布前固定本次完整修订，服务端以该修订生成版本，之后继续编辑不会改变已提交内容。只改提示词时发布新的 Agent 并复用原 Skill；Skill 改动则与受影响 Agent 一起发布，所有新标签由运维手填。

结果：一次本地改进成为团队可复用、可追溯的正式资产，新会话使用所选新版，旧会话保持原快照。周内反复迭代，按周发布已确认内容，执行反馈继续推动下一次改进。图示为目标业务流程；当前草稿实验与本地完整会话快照已实现，官方发布同步仍待接入，完成情况见第 08 章。

### 场景三：运维在调试桌面主动发起会话

前提：运维人员在调试桌面选择官方 Agent，准备检查成功，本会话没有活动轮次且并发容量可用。本地 Agent 使用本地装配；引用官方 Skill 时仍需补齐对应版本。这是本地调试入口，线上用户的业务请求从服务端 Console 进入。

![运维在调试桌面主动发起会话](./assets/runtime/00-manual.svg)

[打开顺序图：运维本地调试会话](./diagrams/runtime/00-manual.html)

结果：调试桌面保存并展示本轮结果，等待运维继续输入时释放运行容量；同一会话保留页面并继续使用开始时的快照，其他会话可以并发执行。

验收从客户端操作或远端调用进入，覆盖“编辑发布 → 同步装配 → 调用执行 → 结果恢复”的完整结果。[规格依据：Issue #3](https://github.com/time-gift24/omniops-bots/issues/3)。

## 服务端配合

为支持上述客户端能力，已有内部服务需要提供：

- **身份与权限**：复用已有账号与 Token，返回用户身份与运维权限，并校验官方资源写入；普通用户不能写入官方资源。
- **线上业务入口**：Console 承载用户业务请求、任务状态与结果查看；服务端 Agent 决定何时调用客户端能力并消费结果，客户端只向线上用户提供基础状态信息。
- **草稿、发布与同步**：接收运维在客户端确认后提交的完整内容；按需保存草稿修订，正式发布时保存不可变版本并提供 HTTPS 清单与文件包。Skill 正式发布联动受影响 Agent，所有标签由运维人员手填，提交即确认，不增加审核。
- **资产持续演进**：保留每周发布涉及的提示词、Skill 和 Agent 装配关系，让客户端能够查看新旧版本及本次改进；不为周发布新增定时自动发版、MCP 发布或独立提示词版本系统。
- **调用与结果确认**：服务端 Agent 在编排中使用标准 A2A 调用客户端的确定版本入口；以 messageId 去重、taskId 查询或取消，持久接收状态、结果与非敏感运行摘要后通过已声明扩展确认。WSS 只负责传输，忙时返回 REJECTED Task，后续新执行使用新消息 ID。
- **桌面更新来源**：提供更新清单和已签名整包下载，供客户端检查、下载与校验。
- **诊断接收**：接收用户指定 thread 的诊断包，校验并持久保存后返回回执，支持运维按编号只读查看；不会因此恢复或重新执行任务。

应用角色拆分、跨机器 Compose、网关多实例与共享文件存储见[核心 · 服务端部署与持久化](./核心-服务端部署与持久化.md)；当前单机 Nginx 仍是入口单点，服务端方案待实施。客户端依赖的 HTTPS API、A2A 操作、WSS 绑定和接收确认契约统一见 [10 · 服务端 API](./10-服务端API.md)。
