# 核心 · 服务端部署与持久化

**将原来同时处理 Console 请求和执行图的 3 个 worker，调整为 API、WebSocket 网关、图 worker 三种运行角色。每台应用服务器用同一份 Docker Compose 启动，连接同一套 PostgreSQL、Redis 和共享文件存储。** 承接[上一章：Agent 版本管理](./前置-Agent版本管理.md)，本章说明确定版本的 Skill／提示词如何存放、系统如何部署；随后进入[客户端需求与职责](./00-总体架构.md)，再到[核心 A2A 章节](./核心-服务端通过WS调用客户端.md)说明确定版本如何被调用。Skill 模板章节仍放在核心最后。

本章是外部服务端的**目标部署方案，待实施**。已确认的现状是：单机 Nginx 做负载均衡，3 个 worker 同时承担 Console 交互和图执行，通过 Make 启动，已有共享 PostgreSQL 和 Redis 消息队列。服务端源码、镜像入口、队列实现与基础设施配置不在本仓，以下不作为已上线或已验证的容器能力。

## 单机改造前后：先分职责，再扩到多机

**第一步可以先在一台应用机器上用 Compose 完成改造：保留 3 个图 worker，把 Console API 和 WebSocket 网关拆成独立运行角色，接入统一持久化。第二步再在其他机器启动同一套 Compose，形成应用多实例。** 后文多机部署图展示第二步的目标形态；单机容器化本身不提供整机故障容错。

### 改造后：一台机器先用 Compose 分开运行

### 随后扩容：另一台机器接同一套共享依赖

![跨机器 Compose：共享状态、队列和文件，单机 Nginx 仍是入口单点](./assets/server-deployment/topology.svg)

[打开跨机器部署图](./diagrams/server-deployment/topology.html)

第二台机器使用同一镜像与共享配置启动 Compose，原来 3 个 worker 示例分成 A 机器 2 个、B 机器 1 个；API、网关跨机各有两个实例。新增 API／网关显式加入 Nginx upstream，worker 连接原队列；需要容错的每种图都有兼容替代实例。单机 Nginx 仍是入口单点，PostgreSQL、Redis、NAS 的高可用也要独立保障。

改造首先解决职责耦合、发布方式和跨 worker 持久交接，使后续增加机器不依赖原 worker 的内存与本机文件。单机阶段不增加原有图 worker 总数，也不宣称吞吐一定提高；API、网关与 worker 仍共享该机器的 CPU、内存和网络。NAS、PostgreSQL、Redis 的部署位置与可用性独立核实，不能仅凭“共享”认定已经跨机或高可用。

## 先看文件位置：Skill、提示词与运行目录

![共享文件系统中的 Skill、Agent 提示词和运行目录](./assets/server-deployment/filesystem.svg)

[打开文件系统目录图](./diagrams/server-deployment/filesystem.html)

**图中根目录是各应用机器挂载的同一个 NFS 导出，文件位置属于目标服务端。** 桌面端按需下载物料，保持正式包的相同相对路径；其本地根目录与运行记录仍独立，不直接挂载服务端 NFS。图只展开正式物料和运行目录，草稿路径另见下表；可选的 `scripts/`、`references/`、`assets/` 不要求每个 Skill 都创建空目录。

| 内容 | 相对共享根的文件位置 | 与版本／执行的关系 |
| --- | --- | --- |
| Agent 完整系统提示词 | `agents/releases/<agentId>/<contentId>/prompt.md` | 随 Agent 包固定，不单独建立一套 Prompt 发布标签 |
| Agent 装配清单 | 同版本目录中的 `agent.json` | 固定 `skills[]` 中的 `skillId`、Skill `contentId` 和 `mountPath`，以及 tool／MCP 配置；不复制成另一份 Skill 包 |
| Skill 完整包 | `skills/releases/<skillId>/<contentId>/` | 入口是 `SKILL.md`，脚本、参考文件和资源按包内原结构保存；整个包决定该 Skill 内容 ID |
| 已保存草稿修订 | `agents/drafts/<agentId>/revisions/<draftRevisionId>/`、`skills/drafts/<skillId>/revisions/<draftRevisionId>/` | 保存完整不可变修订，不作为正式发布版本；本机可编辑 working 副本不等同于服务端正式物料 |
| 运行时工作目录 | `workspaces/<组织>/<workspaceId>/` | 保存获准运行可修改的文件，不能写回正式 Agent／Skill 包 |
| 运行产物 | `artifacts/<组织>/<serverRunId>/` | 截图、报告等由确定运行产生，索引与权限在 PostgreSQL |

一个 Agent 的 `agent.json` 可以引用多个确定 Skill 包；只改 `prompt.md` 就发布新的 Agent 内容版本，Skill 包可继续复用。运行时先解析到固定内容 ID，再以只读版本文件装配 Agent；模型和推理参数参与后续运行指纹，不写进这些正式版本文件。完整包格式与摘要规则沿用[Agent 版本布局](../agent-version-layout.md)和[Skill 版本布局](../skill-version-layout.md)。

阅读主线由此展开：**Agent 版本管理固定组合与运行指纹 → 本章说明物料位置与部署方式 → 总体章节说明 Console／服务端／桌面职责 → A2A 选择确定 Agent 入口并创建独立 Task。** 文件位置解决“字节在哪里”，版本身份解决“用哪一份”，A2A 解决“如何调用和交付”，不能用共享目录或 `contextId` 自动恢复桌面执行现场。

## 从当前部署到目标部署

跨机器形态见本章头部的[部署交互图](./diagrams/server-deployment/topology.html)，以下按运行角色补充职责与扩容边界。

| 角色 | 当前 | 目标职责与扩容方式 |
| --- | --- | --- |
| Nginx | 单机入口，分发到 3 个 worker | 沿用入口，分别代理 Console API／实时连接与桌面 WSS；应用跨机器扩容后显式更新 upstream |
| API | 由 worker 同时承担 | 接收 Console 请求、鉴权、资源管理、运行查询与现有实时交互；发起执行先保存记录，再通知队列；不在请求进程中执行图 |
| WebSocket 网关 | 远端桌面接入待实现 | 管理已鉴权连接、心跳、有界收发、重连与流清理；装配独立的 A2A 客户端处理模块，后者负责调用关联、结果持久化与交付确认；不执行图 |
| 图 worker | 3 个进程执行不同图，并直接交互 Console | 只领取允许执行的图任务，装配 Agent、调用模型／工具、保存状态与产物；结果通过共享记录和通知交给 API／网关 |
| 文件能力 | 存放位置与跨机器共享待明确 | API 内的文件模块负责鉴权、索引和上传下载；NAS／NFSv4 负责文件字节和工作目录；不另造通用文件微服务 |

三种应用角色可以使用同一份服务端镜像、选择不同启动入口；共享业务模块，按角色分别运行。单机验证阶段总 worker 数保持 3；进入应用节点容错阶段，再把这 3 个 worker 分布到至少两台应用机器，API 与网关也至少各有两个跨机器实例。单台机器只需启用本机承担的角色，不能把两台机器各启 3 个 worker 误写成原来的总容量。

如果某种图只有一个 worker 能运行，它仍只有一个执行实例。需要保障的每种图应至少有两个兼容实例可处理；复用已有队列的图类型选择、运行租约和同 run／thread 互斥。实际能否接管进行中的服务端 run，取决于现有图引擎与持久化策略，不能仅因增加副本就承诺自动恢复。

## Console、worker 和桌面调用如何衔接

![Console 请求与跨 worker 的持久结果交接](./assets/server-deployment/handoff.svg)

[打开 Console 与 worker 交接顺序图](./diagrams/server-deployment/handoff.html)

**前提：**图中 worker 1 负责原执行，后续步骤由现有运行机制允许的 worker 2 领取；这不是让任意 worker 同时修改同一个运行。

API 先持久保存业务 run 和待调度记录，再向 Console 返回运行身份。Redis 队列消息引用持久记录；运行状态、调用意图和最终结果不能只放在某个 worker 的内存回调里。Console 的后续请求可以落到其他 API 实例，仍从共享存储取得同一 run 的状态；实时连接沿用 Console 现有契约，不绑定执行 worker。

调用桌面前，持久保存目标安装、确定 Agent 版本、稳定 `messageId` 与服务端 run／步骤的关联。网关收到通知后，只对本机持有的目标连接发送 A2A 请求；首次受理响应保存原 `taskId`。更换 worker 或网关时，沿用原调用身份，不能生成新 `messageId` 再执行一次。

桌面最终结果由接入进程中的 A2A 处理模块接收：**同一数据库事务保存原 Task／结果索引及待推进记录，提交后才能发送既有交付确认扩展。** 后续推进通过原运行队列处理，使用唯一约束、条件更新与已有运行互斥做幂等；重复结果不能重复产生下一步。确认不依赖最初那个 worker 仍存活。

结果若引用文件，先完成文件持久化与授权索引，再确认结果交付；保存一个失效的临时下载地址或另一台机器不可达的本机路径，不算已经持久接收附件。

PostgreSQL 与 Redis 不能当成一个跨系统原子事务。待派发、待入队和待推进记录先留在 PostgreSQL，通知失败、进程退出或队列丢失后，复用服务端后台处理检查未完成记录并重新通知；重复入队仍须幂等领取。已有可靠 outbox／调度机制能覆盖时直接复用，不另建一套调度框架。

## 网关多实例与断线恢复

![网关 A 退出后经原 Nginx 连接网关 B](./assets/server-deployment/gateway-reconnect.svg)

[打开网关切换顺序图](./diagrams/server-deployment/gateway-reconnect.html)

**前提：**Nginx 及共享依赖仍可用；故障是网关 A 退出，桌面进程没有重启。已有 WSS 不迁移到网关 B，而由桌面重新连接。

当前规模使用 Redis Pub/Sub 广播小型唤醒通知，各网关检查目标安装是否连接在本机。不要让所有网关在同一个竞争消费组随机领取下行调用：领取者可能没有目标 socket。暂不建立全局连接发现平台；网关数量或广播量成为瓶颈时，再考虑定向路由。

Pub/Sub 只负责提醒，不保存唯一业务事实。Redis 官方定义它为 at-most-once，离线期间的通知会丢失；网关在连接建立、订阅恢复及定期核对时查询 PostgreSQL 中仍待处理的调用与交付记录。数据库中的工作不会因一次通知丢失被标记完成。[Redis Pub/Sub 交付语义](https://redis.io/docs/latest/develop/pubsub/)。

连接按已鉴权组织、调用方与安装隔离；并发重连可能短暂保留旧连接，持久幂等仍必须成立，旧连接清理不得删除新连接的本机映射。网络层的连接身份不进入 A2A 业务对象，也不以安装地址代替授权。

恢复沿用标准 A2A：未知 `taskId` 时以原 `messageId` 重投；非终态用 `SubscribeToTask`，已终态用 `GetTask`；未确认结果继续交付。不补播历史事件，不增加私有恢复消息。桌面断线继续执行、重启不续跑的约束保持不变。

Nginx 明确转发 WebSocket `Upgrade`／`Connection`，上游读取超时与心跳配合；Console 若采用流式响应，还应沿用其现有缓冲与超时要求。计划发布先摘除新连接与任务准入，再限时排空，客户端退避并加抖动重连。[Nginx WebSocket 代理说明](https://nginx.org/en/docs/http/websocket.html)。

## 一台与多台机器怎样用 Compose 启动

每台机器运行同一份应用 Compose，镜像版本、共享端点、环境与队列命名空间一致；本机名称、端口和副本数可以不同。应用 Compose **不重复创建 PostgreSQL、Redis 或独立文件服务器**。测试环境的单机依赖可以另用独立 Compose，但不能复制到第二台后形成两套互不相通的数据。

| 配置 | 跨机器保持一致 | 每台机器独立 |
| --- | --- | --- |
| 应用与兼容性 | 经兼容验证的镜像版本、协议、数据库 schema、队列命名空间 | 发布批次与容器实例身份 |
| 共享依赖 | PostgreSQL 地址、Redis 地址与数据库／前缀、NFS 导出 | 同一共享依赖的本机挂载与受限凭据文件路径 |
| 身份认证 | 会话／签名配置、授权规则，必要会话数据存共享库 | 节点身份；不能将登录会话仅存在 API 内存 |
| 网络 | 私网路由、名称解析、防火墙与传输安全策略 | Nginx 可达的私网地址、API／网关映射端口 |
| 文件访问 | NFS 导出、目录协议、匹配的 UID／GID 和授权范围 | 本机临时目录与可丢弃缓存 |
| 容量 | 每种图的兼容 worker 范围与并发规则 | 本机 API、网关、worker 副本数与资源限制 |

普通 Compose 的 bridge 网络与服务名只作用于对应 Docker 主机；相同 network／volume 名称不提供跨机器共享。第二台机器通过可达的私网地址连接共享服务。新增 worker 可领取同一队列；新增 API／网关还要将该机器的映射端口加入 Nginx upstream，配置检查成功后平滑 reload。Compose 本身不负责跨主机调度、服务注册或自动修改 Nginx。[Compose 网络说明](https://docs.docker.com/compose/how-tos/networking/)。

[应用 Compose 契约示例](./deployment/compose.example.yaml)展示服务拆分、共享 NFS 与凭据文件挂载。它要求外部服务端镜像实现 `api`、`gateway`、`worker` 三个入口并读取指定配置；**当前没有该镜像与入口的实现证据，示例不是可以直接部署现有服务端的交付包**。端口、停止预算和目录是本方案的示例值，实施时应与实际进程契约核对。

服务端仓库落地时交付 Dockerfile、真实入口、`compose.yaml` 与本地部署配置。Make 可以保留为 Compose 的薄封装，不再绕过容器另启动一套 worker。两台机器的命令形态如下；`node-a.env`／`node-b.env` 只保存本机部署参数，凭据放受限文件，不提交仓库：

```sh
# 机器 A：2 个 worker；API 与网关各 1 个实例
docker compose --env-file node-a.env -f compose.yaml config --quiet
docker compose --env-file node-a.env -f compose.yaml up -d --scale worker=2

# 机器 B：连接相同共享服务，再增加 1 个 worker
docker compose --env-file node-b.env -f compose.yaml config --quiet
docker compose --env-file node-b.env -f compose.yaml up -d --scale worker=1
```

镜像应固定版本或 digest，不用 `latest`；正式部署不挂载源码，不给应用挂 Docker socket。数据库迁移由一次受控部署步骤执行，不能每个副本并发迁移。进程接收到关闭信号时停止准入／领取，排空并关闭资源；`restart` 只负责容器重启，不能等同于业务重跑。就绪检查需确认本角色必需的共享依赖；依赖失效时拒绝新工作、保留未确认记录，恢复后重新核对。

## 文件服务：先用一个共享文件系统

用户确认的持久化范围包括 **Agent／Skill 版本物料、运行时可修改工作目录和运行产物**。本期推荐优先选成熟的托管 NAS 或已有高可用 NFSv4.1 服务，让 API 与 worker 直接挂载同一导出；API 的文件模块提供对外访问。这是推荐选型，NAS 产品、地址、容量、备份与可用性尚待实施确认。

这个范围需要普通目录与文件读写，先用共享文件系统可复用已有文件工具和包布局，不为运行时文件另写 S3 文件系统适配器。Docker 支持通过 volume 驱动挂载 NFS；各主机同名 volume 背后必须显式指向同一个 NFS 导出。[Docker NFS volume 说明](https://docs.docker.com/engine/storage/volumes/#create-a-service-which-creates-an-nfs-volume)。

![版本发布、工作目录写入与跨 worker 读取](./assets/server-deployment/files.svg)

[打开文件持久化顺序图](./diagrams/server-deployment/files.html)

| 数据 | 权威存放位置 | 写入与读取边界 |
| --- | --- | --- |
| 业务身份、run／Task 关联、结果索引、文件权限、工作区身份与修订 | PostgreSQL | 数据库约束、事务和现有运行互斥；Redis 不承载唯一副本 |
| 服务端图状态与 checkpoint | 沿用图引擎支持的共享持久后端，优先复用现有 PostgreSQL | 不留在单个容器的内存／本机 SQLite；具体 checkpointer 在服务端核实 |
| Agent／Skill 正式包与草稿修订 | 共享 NFS：`agents/`、`skills/` | 继续采用既有正式版本布局；已发布内容不可变，运行时只读 |
| 可修改工作目录 | 共享 NFS：`workspaces/<组织>/<workspaceId>/` | 服务端显式分配身份、限定授权根目录；同一工作区同一时刻只有一个获准写入的运行 |
| 截图、报告和其他产物 | 共享 NFS：`artifacts/<组织>/<serverRunId>/` | 写入完成并校验后公布索引；终态引用确定文件修订／摘要 |
| 缓存、临时文件 | 容器临时目录或本机缓存卷 | 可以重建；不作为工作目录、版本全集或唯一产物副本 |

根目录示例为 `/srv/omniops-data`。正式物料相对路径完全沿用[Agent 版本布局](../agent-version-layout.md)和[Skill 版本布局](../skill-version-layout.md)，不因服务端换存储而重命名客户端文件协议。`workspaceId` 是服务端持久工作区身份，不由 worker 地址或容器 ID 生成；跨 worker 访问要传入同一授权工作区。它也不等同于 A2A `contextId`，不会让不同桌面 Task 自动共享本地 thread、页面或执行现场。

标签映射与发布可见性以 PostgreSQL 已提交记录为准；既有 `tags.json` 格式保留，作为该记录的读取投影或可重建文件镜像。API 不能从未提交的标签文件公布新版本，也不直接公开整个 NFS 根目录，让文件暂存绕过发布事务。

Deep Agents 文件工具通过现有 backend 访问受限工作根；选用的实际 SDK 若已有 FilesystemBackend，优先复用。纯虚拟小文件／记忆可以使用框架已有持久 Store，但不能把 Store 文件或对象存储当作 shell、第三方工具可直接使用的 POSIX 工作目录；本文不要求切换现有图框架。[Deep Agents backend 分工](https://docs.langchain.com/oss/python/deepagents/backends)。

### 文件写成功与业务提交是两个边界

1. 发布包、完整文件或产物先写入同一共享文件系统的暂存位置，校验大小、文件清单与摘要，完成必要的 flush／close，再用所选文件系统支持的原子重命名公布完整文件／目录。不能暴露半包，不能假设本机 `write()` 返回就等于远程持久完成。
2. 文件可读且满足存储持久性约定后，提交 PostgreSQL 中的版本索引、文件修订或业务结果。文件系统和 PostgreSQL 没有跨系统原子事务：写文件后数据库失败，只留下未公布暂存／孤立文件；不得反过来先发布一个不存在的文件。重试检查原身份、内容与索引，避免生成第二份业务结果。
3. 可修改工作区由获准的运行单写，文件工具采用临时文件替换等方式避免截断已有内容；读者在已提交边界后重新打开文件。工作目录会保留崩溃前已写入的内容，不承诺与图 checkpoint 一起回滚，也不因看见文件就认为对应外部操作或整个 run 成功。
4. 队列租约与数据库版本不能撤销旧进程已经发出的 NFS 写。运行失去所有权应停止写；只有确认旧写者停止、必要锁释放后才能交给下一写者。网络分区无法确认时停止该工作区的新写入，按既有失败／人工核对策略处理，不宣称租约超时即可安全双写。需要分区期间自动接管时，必须另行具备存储侧 fencing 能力。

具体 NAS 的 close／fsync、可见性、重命名和锁行为必须验收。例如 EFS 提供 NFS close-to-open 语义，其锁为 advisory，并不会自动阻止不遵守锁的写入；其他 NFS 产品不能直接套用 EFS 的持久性保证。[文件一致性与锁说明](https://docs.aws.amazon.com/efs/latest/ug/features.html)。

### 对外文件访问与权限

文件能力复用现有资源、发布和诊断 API，正文格式继续见[第 10 章](./10-服务端API.md)，本章不新增公开端点或第二套上传协议。工作区／产物访问归原 API 文件模块；如果实际服务端还没有相应入口，实施时须结合真实调用方补齐完整公开签名、输入输出、错误分类、取消清理与调用示例，再接入。调用方使用受控资源身份、相对路径与必要的预期修订，不能取得宿主机真实路径；此处的存储建议不表示接口已可调用。

API 从已鉴权组织与资源归属解析目录，拒绝绝对路径、`..`、越根符号链接和未授权工作区；限制单文件／包大小、路径、数量与配额。发布冲突、修订冲突、权限拒绝、文件不存在、存储不可用分别传播安全错误，不能伪造空文件或成功。上传取消清理本次暂存，保留已提交版本；下载取消只释放流和句柄。

运行用正式物料只读；工作目录与产物按组织、业务工作区和运行隔离。带 shell／原生工具的执行不能仅靠路径前缀当安全沙箱，需使用受限挂载／既有执行隔离；不能让模型或用户指定任意 NFS 根目录。外部用户不直接访问 NFS，不公开列出整个共享根，也不把共享存储凭据下发给桌面。

初期直接由 API 流式上传下载。大文件分发量或存储规模增长后，可以将不可变版本包与产物迁移到 S3 兼容对象存储，保留 PostgreSQL 权限与索引、NFS 工作目录和现有 HTTPS 契约；按需求使用成熟存储 SDK，暂不增加对象存储和第二套文件平台。预签名 URL 是后续可选能力，需有过期和授权范围，不能把它当永久文件身份。[S3 预签名上传机制](https://docs.aws.amazon.com/AmazonS3/latest/userguide/PresignedUrlUploadObject.html)。

## 可用性边界与迁移验收

| 部分 | 本次目标 | 仍需明确的边界 |
| --- | --- | --- |
| API／网关／worker | 两台以上应用机器独立 Compose，共享状态与文件 | 剩余节点容量、每种图兼容实例及实际运行恢复策略 |
| 入口 | 复用当前单机 Nginx | **仍是单点**。完整入口 HA 需云负载均衡，或网络支持下的双 Nginx＋VIP；本次不将任意网络都支持漂移 VIP 写成事实 |
| PostgreSQL／Redis | 复用现有共享实例／集群 | 共享不代表已经 HA；需核实副本、故障切换、持久化、备份和可接受的数据丢失窗口 |
| 文件存储 | 共享 NAS／NFSv4.1，API 提供访问 | 优先成熟 HA 产品；单机 NFS 容器只是新增单点，同一路径在两台机器分别创建也不是共享 |
| 备份恢复 | 保留数据库记录与其引用的文件 | 定义协调备份点、恢复顺序并验证索引与文件一致；应用多副本不能代替备份 |

实施顺序：先固定运行镜像与三种入口，接共享配置和文件根；将 Console 接入迁到 API、图执行留在 worker；再落地网关与 A2A 持久调用／结果交接；机器 A 验证后在机器 B 用同一 Compose 接入，最后更新 Nginx upstream。旧 Make 入口切到 Compose，逐步排空旧 worker，避免新旧路径同时推进同一运行。

服务端实施时至少验收：机器 B 直接领取同一队列；同一图可由另一兼容实例处理；跨 API 查询同一 run；网关退出后恢复原 Task；原 worker 退出后结果仍能落盘；重复通知／入队／结果不重复推进；Redis 通知丢失后能核对恢复；文件半写、数据库提交失败和 NFS 失联不发布假成功；另一台 worker 重新打开同一工作区与已发布文件；单机 Nginx 故障会造成入口中断。进行中的图和写者的接管限制必须按上述策略验收，不以容器自动重启代替业务验证。

本次只交付文档、部署契约示例和图形，不修改桌面执行路径，不新增日志、span 或指标。服务端实施时复用既有安全日志与错误边界；新增观测项目、字段和统计口径另按项目规范确认，禁止记录凭据、文件正文、提示词或原始 A2A 报文。
